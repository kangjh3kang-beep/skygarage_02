# DOELV 통합관리시스템 구축과 검증 계획

기준 버전: 2026.10-v1 · 조사일: 2026-10-19 KST · 대상: skygarage_02 / skygarage_01 Supabase

이 문서는 본사 통합관리, 단지·현장 관리, 하드웨어, 자동화, LLM 개선 체계를 하나의 검증 가능한 구축 계획으로 연결한다. 현재 운영 가능한 범위와 코드만 존재하는 범위를 분리한다. 36개 요구사항 전체의 인수 증거가 확보된 상태를 목표 달성으로 정의한다. 본 문서 작성이나 단위시험 통과만으로 실장비 운행을 승인하지 않는다.

## 후속 구현 상태 (2026-10-19)

[현장 검증·피드백·성장 루프 구현 패키지](FEEDBACK-LOOP-RELEASE.md)를 별도 검토 브랜치에서 구현했다. 운영 DB 자동 승인 검토가 테이블·권한·예약 작업·자동 현장 중지의 적용을 차단했으므로 이 후속 패키지는 아직 운영 반영 전이다. 아래 v1 운영 기준선과 구분한다. 현장 증거 원장·독립 검수, 조직/현장 역할, 기본 모듈 구축 outbox/inbox, 실패→개선→재검증 흐름, 현장별 인수율 계산을 포함한다.

## 1. 현재 결론과 이번 보강

현재는 입주민 계정·요청 접수와 검증용 단지 생성 기반을 갖춘 검수 준비 단계다. 통합관제·장비·워크플로우·AI 화면 및 Python 모형이 있지만, 하나의 실운영 파이프라인으로 연결·인수된 증거는 없다. 구 시스템의 장비·AI·워크플로우 Edge Function 8개는 검수 대기 응답으로 교체되어 있다. 실제 배포된 hardware-gateway의 소스를 확인했으며 운영 명령은 503으로 거부한다. 함수가 ACTIVE라는 배포 상태는 운행 가능이라는 뜻이 아니다.

이번 구현은 다음 범위다.

| 보강 | 실제 반영 범위 | 완료로 보지 않는 범위 |
|---|---|---|
| 관리자 구축·검증 화면 | `/admin/implementation`, 6단계·36요구사항, 검색·단계 필터·JSON 내보내기 | 영속 인수 증거 원장, 독립 승인 |
| 실제 DB 상태 조회 | super_admin + aal2 전용 집계 RPC, 서버 시각, 누락 응답 거부 | 장비 온라인 판별, 제조사 상태 확인 |
| 명령·미션 계약 모형 | 중복·범위·TTL·fencing·ACK 유실·상태 전이 시험 | 네트워크 전송, 영속 큐, 실시간 안전제어 |
| 기존 요청 화면 | 최초 조회 중/오류/확정 0건 구분, 실패 후 오래된 목록 숨김 | 현장별 요청 배정과 SLA |
| 기준과 시험 자동화 | 소스·시험·요구사항 연결, CI 정의 | HIL·SAT 및 실제 관리자 인증 후 화면 인수 |

이번 계획의 “소프트웨어 검증”은 명시한 코드·시험 범위에 한정된다. 통합 운영 인수 승인 수는 0/36으로 시작한다. 기존 소프트웨어 성과를 0으로 평가하는 수치가 아니라, 새 통합 운영 범위의 독립 인수 증거가 아직 등록되지 않았음을 나타낸다. 현황판 승인 수는 정적 기준선이며 증거 원장 구현 전에는 자동 갱신되지 않는다.

서버 조사: 실제 프로젝트의 테이블·정책·GRANT·함수·마이그레이션·배포 Edge Function 확인. 민감정보는 조회 결과나 계획에 포함하지 않았다. 장비·AI 관련 기존 테이블의 브라우저 권한은 회수되어 있고, RLS 정책이 없는 테이블은 기본 거부 상태다. 조사 당시 보안 점검기의 RLS 정책 없음 INFO 107건은 기능을 개방하라는 의미로 해석하지 않는다. 모듈별 권한 검증 후 필요한 범위만 열어야 한다.

기존 `platform_generate_site`와 신규 집계 RPC의 SECURITY DEFINER는 좁은 서버 역할·aal2 확인과 빈 search_path를 사용한다. 보안 점검기에 authenticated 실행 경고가 나타날 수 있다. 익명 실행 금지, 위조 metadata 역할 거부, 실제 DB 역할 확인 및 최소 반환값을 회귀시험으로 관리한다.

핵심 결함은 “화면·테이블·모형은 많지만 현장 ID, 서버 권한, 상태 전이, 실장비 계약, 인수 증거를 잇는 경로가 부족하다”는 점이다. 기존 시연 데이터나 UI의 선택된 단지를 서버 권한으로 사용하지 않는다. Python 167개 시험은 소프트웨어 모형의 결과이며 배포된 엣지 제어기나 인증된 안전장치의 검증으로 대체하지 않는다.

## 3. 목표 구조와 책임

| 계층 | 책임 | 권한과 경계 |
|---|---|---|
| 본사 통합관리 | 조직·가맹·계약·템플릿·정책·다현장 지표·출시 승인 | 본사 역할, MFA, 감사; 현장 권한과 역할 구분 |
| 단지·현장 서비스 | 회원·세대·차량·방문·요청·운영자·자원·미션 | tenant_id/site_id를 DB·API·파일·이벤트 전체에 강제 |
| 서비스 조정 계층 MOS | 정책·자원 점유·작업 순서·분산 작업·대사 | 상태기계, CAS, TTL, fencing; 네트워크 응답을 물리 완료로 추정하지 않음 |
| 엣지 게이트웨이 | 장비 신원·벤더 프로토콜·명령 수신·현장 이벤트 | mTLS, durable inbox, sequence/epoch, 허용 endpoint |
| 설비·독립 안전 제어 | 로봇·승강기·게이트·센서·충전기·인터록 | 제조사 제어기와 현장 안전 설계; 비상정지/PLC는 클라우드·LLM과 독립 |
| 데이터·LLM | 조회·검색·원인 분석·개선안·예지보전 | 최소권한 도구, 현장별 검색, 평가·승인·회귀·복귀 |

본사는 정책과 기준을 내려보내고 현장은 승인된 설정으로 운영한다. 장비 결과는 같은 미션·이벤트 식별자로 본사·현장·데이터 계층에 전달한다. 각 시스템이 모든 시스템에 직접 호출하는 방식 대신 공통 계약을 통해 연결한다. 동기 API는 즉시 조회·접수에, 비동기 이벤트는 실행·알림·대사에 사용한다. 안전 제어는 제조사와 안전 담당자가 정한 로컬 제어 주기에 따른다.

### 데이터 기준과 격리

목표 관계: organization/tenant → site → building → zone → resource/device. 주민 user와 site membership, 차량과 소유/위임 관계를 별도로 둔다. 기존 complexes와 platform_sites는 검증된 매핑 테이블로 연결하고, 이름 일치만으로 자동 병합하지 않는다. 서로 다른 단지를 하나의 tenant로 묶는 기준은 운영 계약에 맞춰 확정한다.

모든 업무 행·작업·장비 이벤트에 tenant/site를 붙이고 FK로 소속을 보장한다. 현장별 역할은 `(user_id, site_id, role, valid_from, valid_until, revoked_at)` 형태의 서버 정책으로 검사한다. 브라우저의 ContextSwitcher는 표시 선택 기능이다. 각 RPC·Storage·Realtime·검색에서 서버가 권한을 다시 검사한다. 본사 집계도 승인된 본사 역할에만 허용한다.

기존 데이터 이전은 백업 → 출처/시연 여부 판별 → 별도 영역 격리 → ID 매핑 → dry-run → 건수·합계·관계 대사 → 제한 전환 순서다. 개인정보, 결제 원장, 실제 물리 이벤트는 단순한 템플릿 초기화나 롤백으로 삭제하지 않는다.

## 4. 단지·현장 템플릿과 구축 자동화

현재 residence-foundation/1.0.0은 아파트·오피스텔·복합 단지의 명칭·세대·주차 수와 안전한 초기 구성만 생성한다. 회원·관리자·차량·인증키를 복사하지 않고 모든 운행·출입·결제를 비활성 상태로 둔다.

확장 템플릿은 아래 모듈을 조합하되 계약과 장비 capability에 따라 제공 범위를 결정한다.

| 모듈 | 필수 선행 | 현장별 구성 | 검수 전 동작 |
|---|---|---|---|
| 기본 거주·요청 | 조직·현장·권한 | 세대 구조·담당자·운영 시간 | 검증용 데이터 |
| 주차·발렛·직입 | 차량 권리·MOS·장비·안전 | 동선·자원·주차 방식·한계 | 시뮬레이션만 |
| 방문·출입 | 방문 권리·게이트 계약 | 시간·구역·회수 정책 | 출입 허가 없음 |
| EV 충전 | 전력·충전기 계약·정산 | 설비 한도·요금·예약 | 실제 전력/결제 없음 |
| 배송·기타 모빌리티 | capability·자원·서비스 계약 | 작업 종류·구역·시간 | 모의 워크플로우 |
| LLM 운영 지원 | 문서 권리·평가·도구 정책 | 지식 범위·예산·승인자 | 읽기 shadow 단계 |

템플릿 버전은 schema_version, module_versions, digest, dependencies, allowed_overrides, required_gates를 포함한다. 단계는 draft → validated → independently approved → published → deprecated. 현장은 immutable blueprint와 pinned version을 유지한다. 운영 중인 버전을 덮어쓰지 않고 변경 diff·영향·검수 계획을 먼저 생성한다. override는 UI 표시·운영 시간 같은 허용 항목만 수정하며 안전 정책·최소권한을 약화할 수 없다.

자동 구축 작업은 계약 확인 → tenant/site 생성 → blueprint 고정 → 운영자 역할 → 자원 정의 → gateway 등록 → adapter 계약 시험 → 운영자 교육 → 인수 증거 → 현장 승격으로 구성한다. 현재는 첫 검증용 site/blueprint 원자 생성까지 구현되어 있다.

목표 provisioning saga는 DB 상태와 outbox를 하나의 트랜잭션에 기록한다. worker는 lease를 잡고 단계별 idempotency key로 외부 작업을 실행한다. inbox와 결과 갱신은 원자 처리한다. 재시도는 지수 backoff와 jitter, 횟수/시간 한계, DLQ, 담당자 알림을 사용한다. 외부 API 호출 중 DB 장기 트랜잭션을 유지하지 않는다. 보상은 미사용 설정·인증 폐기 같은 가역 작업에만 적용하고 실제 운행·출입·결제는 명시적 대사·환불 절차를 따른다.

## 5. 통합 워크플로우와 하드웨어 계약

표준 서비스 흐름은 요청 접수 → 신원·현장·차량 권리 검사 → 정책·가용성 검사 → 자원 lease → 미션 생성 → outbox → edge inbox → 독립 안전 확인 → adapter → 접수 ACK → 실행 상태 → 실제 완료 확인 → 자원 해제 → 사용자 알림·정산 → 감사·개선 자료다.

명령과 이벤트는 역할이 다르다. 명령은 수행 요청이고 이벤트는 관측된 사실이다. HTTP 성공·메시지 수신 ACK·물리 동작 완료를 각각 별도 상태로 둔다.

| 계약 | 목표 필드와 규칙 |
|---|---|
| 이벤트 | id/source/type/specversion/time/data + tenantid/siteid/missionid/correlationid/causationid/aggregateversion/schemaversion |
| 명령 | command_id, tenant_id, site_id, device_id, mission_id, payload_digest, issued_at, expires_at, fencing_token, capability_version |
| inbox | 수신 주체·범위·event_id 고유키, payload digest 충돌 검출, 처리 결과, 보존기간 |
| 자원 lease | resource_id, holder, expires_at, 증가하는 fencing token, CAS 버전 |
| 관측 | device time + server receive time + device epoch/sequence, 품질·신뢰도·연결 상태 |

CloudEvents 형식을 목표 이벤트 envelope로 활용한다. 자체 extension 명칭은 해당 규칙에 맞게 소문자·숫자를 쓴다. MQTT를 사용하는 경우에도 전달 QoS가 실제 물리 동작의 단일 실행을 보장한다고 가정하지 않는다. 애플리케이션 inbox·명령 중복 방지·대사가 필요하다. 구체 브로커/프로토콜은 제조사 계약과 현장 제약을 확인해 선택한다.

상태기계는 requested → validated → reserved → dispatched → acknowledged → running → completed를 기본으로 한다. 전송 이후 응답 유실은 unknown이며 재전송으로 성공을 추정하지 않는다. 현장 상태를 조회·대사해 reconcile_complete 또는 reconcile_failed로 종료한다. 종료 상태에서 다시 운행하려면 새 승인 작업을 만든다. 잘못된 버전·역순 이벤트는 보류/재조회하고 동일 ID의 다른 내용은 충돌로 차단한다.

이번 TypeScript 모형의 TTL 30초·heartbeat 5초는 계약 시험용 가정이다. Python 게이트 모형의 시간 설정과 함께 실장비 안전 요구사항이나 인증된 제어 주기로 인용하지 않는다. 실제 한계는 위험분석과 제조사 ICD에 따른다.

필요한 제조사 자료는 장비 종류/모델/firmware, ICD/API 스펙, 명령·ACK·상태·고장·취소 의미, 멱등성 지원 여부, 통신/인증/망 구성, 인터록·비상정지·전원 복구 특성, 시험 장비와 담당자다. 제조사 endpoint나 능력을 임의로 가정하지 않는다. capability manifest를 통해 미지원 동작을 차단하고 동일 작업에 다른 제조사 adapter를 끼워도 공통 계약 시험을 적용한다.

### 실패와 복구

| 실패 | 자동 처리 | 사람·현장 확인 |
|---|---|---|
| 중복 요청 | 동일 결과 반환, 내용 다르면 충돌 | 반복 충돌 조사 |
| 구버전 제어권 | fencing 불일치 거부 | 자원 상태 대사 |

| 클라우드 망 단절 | 새 클라우드 미션 중지, 현장 승인된 fail-safe | 제조사 절차에 따른 수동 운용 |
| 게이트웨이 재부팅 | durable inbox·epoch 복원, 상태 조회 | 불일치 장비 격리 |

## 6. LLM 연동과 학습·성장 체계

현재 ai-agent는 검수 대기로 차단되어 있고 운영 모델 레코드가 없다. 이번 변경은 실제 모델 키를 추가하거나 자율 장비 제어를 활성화하지 않는다. 모델 공급자·사용 계약·데이터 처리 조건·예산·배포 지역·평가 모델을 확정한 뒤 서버 gateway를 구현한다.

1. **근거 검색**: 승인된 매뉴얼·현장 설정·장애 이력·작업 절차를 수집하고 버전·출처·site 권한을 저장한다. 조회 시 서버가 사용자와 현장 범위를 강제한다. 근거 부족 시 답변을 유보한다.
2. **운영 지원**: 읽기 도구 `get_site_status`, `search_manual`, `summarize_incident`부터 연결한다. 응답에는 관측 시각과 근거를 포함한다. 이것은 목표 내부 도구 계약이며 제조사 API가 아니다.
3. **제안과 제한된 쓰기**: 티켓 초안·점검 권고·스케줄 후보는 제안으로 생성한다. 실제 변경은 검증된 typed tool, 서버 권한, 위험 등급, 승인, idempotency를 거친다. 모델이 SQL·쉘·제어 endpoint를 자유 호출하지 못하게 한다.
4. **평가**: 현장별 고정 질문·알려진 장애·근거 없는 질문·다른 현장 정보·지시 주입·권한 우회·고비용 루프 시험을 마련한다. 모델·프롬프트·도구·retrieval index·데이터셋 버전을 모두 고정한다.
5. **성장**: 운영자 수정·실제 결과·오탐/누락을 피드백으로 받는다. 사용 권한과 개인정보 처리를 확인한 자료만 개선 후보에 반영한다. 지식/프롬프트 개선 → shadow 평가 → 독립 승인 → 소수 현장 canary → 전체 적용 순서다.
6. **복귀**: 회귀·비용 초과·정보 누출 의심 시 새 버전을 중지하고 검증된 버전으로 복귀한다. 지식 문서가 폐기되면 관련 인덱스도 제거한다. 승인 만료·권한 회수는 검색 캐시에도 반영한다.

자가학습의 첫 단계는 검증된 지식 갱신과 피드백 기반 후보 생성이다. 모델 가중치의 무감독 상시 변경은 기본 설계에 포함하지 않는다. fine-tuning은 별도 데이터 권리·비식별·평가·승인 작업으로 다룬다. 현장 안전 임계값·운행 승인·관리자 권한·결제 원장을 스스로 변경하는 기능은 제공하지 않는다.

초기 평가 기준 제안: 교차 현장 정보 누출/금지 도구 실행 0건, 검증 가능한 답변의 근거 연결 95% 이상, 대표 업무 평가 정확도 90% 이상. 이 수치는 초기 목표이며 검증된 성능 주장이 아니다. 데이터셋 구성과 비용/응답시간 한계는 P4 착수 시 고정한다. 예지보전은 충분한 실제 고장 라벨과 시간 누수 없는 검증이 확보될 때까지 shadow 권고로 운영한다.

## 8. 100% 달성의 계산과 검수

기준선은 `src/lib/implementation-plan.ts`의 36개 ID다. 분모 변경은 계획 버전을 올리고 추가/제외 이유·승인자를 기록한다. 후반에 미완료 항목을 제외해 완료율을 올리지 않는다. UI 구현률·시험 통과율·운영 인수율을 하나로 합치지 않는다.

운영 인수 완료 조건은 해당 요구사항의 모든 완료 조건, 선행 항목, 환경별 시험 증거, 독립 검수자의 승인, 미해결 치명 결함 0건, 유효한 버전 일치다. unknown, skipped, mock, expired 증거는 완료로 계산하지 않는다. 단지별 필수 gate도 각각 통과해야 하며 한 현장의 승인을 다른 현장에 복제하지 않는다.

목표 증거 원장은 requirement_id, plan_version, tenant/site, release_sha, schema_version, template_digest, device/firmware_version, test_kind, procedure_version, environment, result, measured_at, artifact_uri/hash, submitter, reviewer, approved_at, expires_at, supersedes를 포함한다. 시험 실행과 제출, 독립 검수, 사이트 승격을 분리한다. 비밀·개인정보는 증거 파일에서도 제거한다. 코드·모델·설비·설정 변경 시 영향받는 승인을 만료시키고 재시험한다.

| 시험 계층 | 필수 범위 | 통과 근거 |
|---|---|---|
| 정적/단위 | 입력·권한 결정·상태 전이·수치 경계 | 해당 release의 runner 결과 |
| DB/API | 실제 역할·RLS·동시성·idempotency·rollback | 격리된 fixture와 SQL/API 로그 |
| 계약 | 지원/미지원 capability·ACK·오류·timeout | vendor ICD 버전과 adapter 결과 |
| SIL | 중복·역순·유실·재부팅·clock skew·경합 | 재현 가능한 시나리오/seed |
| HIL | 실제 제어기·센서·전원·인터록·안전 회로 | 계측·장치·firmware·서명 |
| SAT | 실제 현장 동선·하중·운영자·비상 절차 | 현장 책임자/안전/제조사 인수 |
| 운영 | pilot·SLO·백업 복원·온콜·교육 | 실측 지표와 훈련 보고서 |

필수 장애 시험: 동일 메시지 10회 재수신, event_id 내용 충돌, 역순·version conflict, 다른 tenant/site 호출, 권한 회수, gateway 재부팅, 명령 직후 네트워크 단절, ACK 유실, lease 만료 중 작업, 시계 전진/후진, stale heartbeat, 비상정지, 센서 불명, 전원 복구, DB 장애, queue 적체, 모델 장애/지시 주입. 물리 동작 결과는 실제 상태 대사로 판단한다.

관측 지표는 성공률·거부율·대기/완료 p95·UNKNOWN 체류시간·outbox oldest age·DLQ 수·장비 가용성·복구시간·LLM 근거율/회귀/비용이다. RTO 1시간/RPO 5분을 관리 데이터 복구의 초기 논의 목표로 제안하되 아직 보장하지 않는다. 제어 시스템의 안전 정지/복구 시간은 별도 안전 설계가 정한다. 부하 목표는 site/device/동시 미션 수를 확정한 뒤 1배/2배/장애 조건으로 측정한다.

## 9. 검증 기록과 배포 원칙

이번 로컬 확인: Node 계약·가입·SMS·템플릿 시험 47/47 통과, Python 모형 시험 167/167 통과. 신규 실제 DB 읽기 검증 6항목은 익명 거부, 위조 metadata 역할 거부, super_admin aal1 거부, super_admin aal2 허용, 장비 수 대사, 제한된 aggregate 응답으로 구성한다. 테스트의 JWT claims는 PostgreSQL 트랜잭션 안에서만 설정하고 rollback하며 사용자의 로그인 세션·권한을 변경하지 않는다. 이는 실제 브라우저 MFA 로그인 시험과 별개다.

배포는 DB의 호환 가능한 읽기 RPC 추가 → 권한 시험 → 웹 build → 범위가 확인된 GitHub main fast-forward → Cloudflare Pages check → 공개 로그인 경계와 인증된 관리자 화면 순서다. 기존 영화/미디어 작업 등 이번 범위 밖의 변경은 포함하지 않는다. 인증된 관리자 세션이 없으면 내부 화면 인수를 미확인으로 기록하고 인증을 우회하지 않는다.

복귀: 웹은 이전 검증된 commit을 새 정상 commit으로 되돌린다. 새 RPC는 읽기 전용이므로 즉시 제거할 필요 없이 실행 grant 회수로 닫을 수 있다. rollback은 이미 완료된 물리 이벤트·입주민 요청·결제 데이터를 지우지 않는다. CI가 추가되어도 Cloudflare 자동 배포가 CI 결과를 자동으로 기다리는 것은 아니다. 후속 출시 gate에서 required checks와 배포 환경 승인을 연결해야 한다.
