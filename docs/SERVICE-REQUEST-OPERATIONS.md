# 현장 요청 배정·기한·답변 운영

기준일: 2026-10-24 KST. 공식 앱의 요청 접수부터 본사/현장 요청함, 담당자 배정, 운영 목표 기한, 검토·답변·반려와 회원 확인을 연결한다. 실제 로그인·문자 수신·운영자 인수와 장비·결제 실행은 별도 검수 대상이다.

## 구성과 사용

| 화면 | 사용 방법 |
|---|---|
| 공식 앱 설정·차량·방문 문의 | 문자 인증을 마친 회원이 요청할 현장과 제목·내용을 선택한다. 활성 소속 현장만 선택할 수 있다. 무소속·다른 시설 이용 문의는 본사 공통 문의로 접수한다. 현장 선택 시 내용 공개 범위를 안내한다. |
| `/admin`, `/admin/tickets` | 최고관리자는 본사 공통·무소속 요청 또는 현장을 선택한다. 현장 담당자는 유효한 담당 현장만 선택한다. 미배정·기한 초과·상태 필터, 최대 50건 페이지와 서버 조회 시각을 사용한다. |
| 상세·배정·답변 | 내용 확인 → 변경 사유 5~500자 → 유효한 담당자와 목표 기한 저장 → 상세 재조회 → 배정된 본인의 검토 시작 → 답변 완료·반려 순서로 처리한다. 완료·반려 답변은 2~2000자다. 종료 후에는 수정하지 않고 후속 요청을 새로 접수한다. |
| 본사 공통 요청의 현장 연결 | 요청자가 실제 이용하려는 현장과 내용 공개 범위를 확인하고 확인란·사유와 함께 연결한다. 요청자의 해당 현장 활성 소속이 필요하다. 연결하면 담당자·기한을 비우고 현장에서 다시 배정한다. 이미 연결된 현장은 변경하지 않는다. |
| `/app/requests` | 본인의 최근 30건에서 현장·상태·답변·목표 기한을 확인한다. 내 요청 새로 조회로 갱신한다. 이전 요청은 접수번호를 적어 운영센터에 문의한다. 소속 해지 후에도 본인 접수 이력은 유지된다. |

목표 기한은 입력 기기의 시간대로 입력·표시하고 서버에는 절대 시각으로 저장한다. 현재 이후 30일 이내이며 비우면 미설정이다. 미배정 상태에는 기한을 지정하지 않는다. 기한 초과는 서버 조회 시각으로 계산하고 종료된 요청은 초과 집계에서 제외한다. 영업시간·공휴일·계약별 SLA, 자동 SMS·알림·자동 에스컬레이션은 이번 범위가 아니다.

담당자 후보는 해당 현장의 유효한 manager 권한을 가진 운영 계정 또는 최고관리자다. 현장 viewer/reviewer는 조회만 가능하다. 본사 공통 요청은 최고관리자만 배정·처리한다. 직원 역할과 회원 소속은 구분하며 요청 처리로 회원 승인·차량 등록·장비 운행·출입·결제를 실행하지 않는다. 사유·답변에 비밀번호·인증번호·불필요한 개인정보를 넣지 않는다.

## 보안·원자성·복구

- 기존 `sgp_service_requests`에 nullable site_id, revision, assigned_to, due_at을 추가한다. 기존 행은 본사 공통 요청으로 남고 원래 내용·상태·답변·감사 이력을 보존한다. 기존 `support_tickets` 자료를 제목이나 이름으로 자동 병합하지 않는다. 기존 검수 차단 페이지를 공식 앱 요청의 업무 화면으로 교체하고 기존 테이블은 삭제하지 않는다.
- 직접 SELECT/INSERT/UPDATE와 과거 컬럼별 INSERT/UPDATE 권한을 회수한다. 회원 읽기·접수, 관리자 목록·상세·명령은 범위가 제한된 RPC로 수행한다. 비공개 명령 영수증·이력 테이블은 RLS를 켜고 모든 클라이언트 역할에 직접 접근을 금지한다. 공개 RPC는 익명·서비스 역할 실행을 금지한다.
- 요청 관련 RPC는 JWT session_id와 실제 Auth 세션·사용자 일치, not_after, 계정 금지·삭제를 검사한다. 세션 행 공유 잠금으로 세션 삭제와 순서를 맞춘다. 관리자는 AAL2와 현재 DB 역할·현장 배정·유효기간도 검사한다. user_metadata를 권한 판단에 사용하지 않는다. 접수는 활성 회원의 서버 문자 인증 상태·시각을 확인한다. 이 검사는 새 문자 수신이나 최근 본인확인의 증명이 아니다.
- 명령은 현재 요청함을 명시하며 다른 현장 요청을 읽거나 변경할 수 없다. 원본 제목·내용·요청자·접수번호는 불변이다. 요청 행 잠금과 revision CAS로 오래된 화면을 거부한다. 담당 권한 만료·회수·계정 차단은 다음 조회·처리 시 다시 검사한다. 권한이 만료된 기존 담당자가 있으면 유효한 담당자에게 재배정한다.
- 상태 변경·담당자·기한·현장 연결, 전체 감사, 비공개 업무 이력·영수증은 하나의 트랜잭션이다. 이력 작성 실패도 본문 변경을 롤백한다. 담당자 사유와 당시 공개 답변은 이력에 보존하며 회원에게는 현재 공개 답변만 반환한다. 관리자 상세는 최근 이력 30건을 표시한다.
- 불확실한 응답은 같은 내용·동일 요청 UUID로 재시도한다. 내용 변경 시 새 UUID를 사용한다. 접수 영수증은 최초 선택 현장으로 비교하므로 나중에 현장 연결이 바뀌어도 동일 접수의 재시도를 인식한다. 현장 연결 명령의 응답이 유실되어 본사 목록에서 이동했어도 원래 영수증을 재조회할 수 있다. 재시도는 새 소속이나 새 권한을 발급하지 않는다.
- 현장·계정·새 조회 키가 바뀌면 이전 응답을 현재 목록으로 표시하지 않는다. 조회 오류에서 과거 요청 목록·상세를 숨기고 다시 조회를 안내한다. 회원의 접수 폼은 계정·분류별로 분리하고 처리 중 입력·중복 전송을 막는다.

기존 4인자 `sgp_submit_service_request`는 본사 공통 접수로 호환한다. 새 5인자 호출은 명시적 site_id/null을 사용해 오버로드를 구분한다. 이전 클라이언트의 직접 테이블 조회·관리자 답변 방식은 사용할 수 없으므로 최신 화면을 사용한다. 데이터가 보이지 않으면 `/app-update`의 화면 업데이트를 이용하고 다시 로그인한다.

## 검증 근거와 범위

- `tests/service-request-database.test.mjs`: 실제 폐기 가능한 DB에서 본사→현장 연결, 다른 현장·타인 접근 거부, AAL1·회수/잘못된 세션 거부, 컬럼 권한 우회 거부, 담당자 자격·CAS·기한·상태·답변 검사, 하위 오류 전체 롤백, 중복 재시도·원본 이력·50건 페이지·기한 초과 집계·회원 소속 해지 후 이력 보존을 시험한다.
- `tests/harness/service-request-journey.mjs`: 실제 React를 같은 SQL에 연결해 회원 현장 선택·접수·배정·목표 기한·검토·최종 답변·회원 조회를 시험한다. 접수·답변·현장 연결 성공 후 응답 유실 재시도, 공개 범위 확인란, 늦은 현장 응답과 조회 실패도 시험한다.
- 테스트 Auth 세션·휴대전화 확인 상태·역할은 명시적 로컬 가상 픽스처다. 운영 DB에는 테스트 계정·문자 인증 성공·가상 세션·요청을 넣지 않는다. CI는 PostgreSQL 17에서 같은 새 계약을 수행하고 기존 권한·금융·ERP·Auth·회원·세대 계약을 회귀한다.
- T05는 일부 구현 상태를 유지한다. 실제 계정·운영자 인수, 실제 업무량 부하, 계약별 SLA·자동 알림, 전체 개인정보 보존·삭제 정책과 기존 CRM/support 데이터 매핑은 남아 있다. 화면 이용 가능은 현장 운영 전체의 인수 승인이 아니다.

## 참고와 채택 판단

[Zendesk의 티켓 생명주기](https://support.zendesk.com/hc/en-us/articles/8263915942938-About-the-ticket-lifecycle-and-ticket-statuses)와 [담당자 배정 안내](https://support.zendesk.com/hc/en-us/articles/4408881925786-Lesson-1-From-support-requests-to-tickets), [Jira Service Management 요청함](https://support.atlassian.com/jira-service-management-cloud/docs/check-out-your-queues/)·[SLA 목표](https://support.atlassian.com/jira-service-management-cloud/docs/create-service-level-agreements-slas/)를 조사했다. 담당자·상태·목표 기한을 한 흐름으로 묶고 미배정·기한 초과 요청함을 채택했다. 우리 현장의 역할·보존·장비 경계에 맞춰 종료 후 자동 재개와 자동 권한 발급은 도입하지 않았다. 계약·영업시간이 확정되지 않아 SLA 달성을 주장하지 않는다.

[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)와 현재 변경 이력을 확인하고 비공개 RLS·빈 search_path·최소 실행 권한·기준 ID·조회/외래키 인덱스를 적용했다. 새 패키지를 설치하지 않았다.
