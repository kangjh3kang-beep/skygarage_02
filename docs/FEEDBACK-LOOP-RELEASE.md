# 현장 검증·피드백·성장 루프 구현 패키지

기준: 2026-10-19 KST / 운영 기준 커밋 `6f3b96722ef630d2458f2784ca92a587d3de3100`

## 적용 상태

2026-10-19 사용자가 공개 GitHub 업로드, 운영 DB 변경, 증거 만료 등에 따른 관리 상태 중지, 후속 배포를 명시적으로 승인했다. 동일 SHA-256의 마이그레이션을 운영 PostgreSQL 17.6에 적용했다. 10개 신규 테이블의 RLS·직접 접근 차단, 12개 신규 RPC의 익명 실행 차단과 빈 search_path, 비공개 helper 실행 차단을 확인했다. 익명·MFA 부족·위조 사용자 메타데이터 요청은 실제 운영 DB에서 거부됐다. 매분 작업의 첫 실행은 2026-10-19 12:37 KST에 성공했다. GitHub CI와 웹 배포의 결과는 연결된 PR/배포 확인 기록에서 별도로 확인한다.

## 이번에 구현한 연결

1. 최고관리자(MFA)가 운영 조직을 등록하고 조직에 속한 검증용 단지를 생성한다. 기존 템플릿의 운행·출입·결제 비활성 설정을 유지한다.
2. 단지 생성과 같은 DB 트랜잭션에 구축 이벤트를 기록한다. 처리기는 허용된 기본 모듈 두 개만 구성한다. 중복 수신은 inbox로 대사하고, 실패는 지수 대기 후 최대 5회 재시도하여 실패 대기열로 옮긴다.
3. 현장 담당자·검수자·조회자를 기존 관리자 계정에 배정한다. 요청마다 DB 역할, MFA, 현장, 권한 만료·회수를 검사한다. 화면의 단지 선택은 권한으로 사용하지 않는다.
4. 현장·계획 버전·소스 커밋·설정 SHA-256에 검증 범위를 고정한다. 새 버전에 과거 승인을 복사하지 않는다.
5. 요구사항별 시험 종류·환경·절차·보고서 링크·해시·결과·측정 시각·유효기간을 저장한다. 등록은 증거의 진위를 자동 보증하지 않는다. 검수자는 파일과 해시, 실제 시험 범위와 완료조건을 확인한다.
6. 실패 결과는 같은 요구사항의 결함 과제를 자동 생성한다. 과제는 접수 → 개선 중 → 새 통과 증거 → 독립 검수 → 완료로 처리한다. 실패와 같은 종류·환경에서 수행한 더 나중의 재시험이 필요하다.
7. 성장 제안도 같은 과제 흐름으로 구현·평가·검수를 연결한다. 자율 LLM 학습·모델 적용을 실행하는 기능은 이번 범위에 없다.
8. 요구사항의 필수 시험 종류와 전체 완료조건 검수, 선행 요구사항, 유효기간, 현재 검수자 권한, 미해결 결함을 서버가 확인하여 인수율을 산출한다. 총 36개라는 분모는 유지한다.

## 화면

- `/admin/governance`: 운영 조직, 접근 가능한 현장, 검증 범위, 증거, 개선 과제, 독립 검수, 현장 담당 권한, 단계 전환.
- `/admin/templates`: 운영 조직 선택을 추가하고 단지 생성과 구축 이벤트를 연결한다.
- `/admin/implementation`: 고정 인수 수치 대신 현장별 증거 원장으로 연결한다.

실제 사용자 로그인·MFA 후 화면 인수는 별도다. 관리형 실행 환경에 지원되는 브라우저 검수 도구가 없어 이번 로컬 작업에서는 브라우저 인수를 수행하지 않았다. 타입 검사·프로덕션 빌드·응답 파서·DB 계약 검증은 구분하여 기록한다.

## 승인받아 적용한 운영 DB 변경 범위

| 변경 | 영향 |
|---|---|
| 비공개 테이블 10개 | 조직·담당 권한·고정 요구사항·검증 범위·증거·검수·개선 과제·outbox·inbox·모듈 구성 저장 |
| 기존 `platform_sites` 열 2개·인덱스 | `organization_id`, `validation_scope_id`; 기존 데이터 삭제 없음 |
| 제한된 공개 RPC 12개 | DB 역할·MFA·현장 범위를 검사하며 비공개 테이블 직접 접근은 금지 |
| 고정 요구사항 카탈로그 | 기존 36개 ID·완료조건·의존성 유지, 필수 시험 종류와 인수 체크 추가 |
| `pg_cron` 확장과 예약 작업 2개 | 매분 내부 구축 큐·증거 유효성 확인, 매일 이 두 작업의 30일 초과 실행 기록만 정리 |
| 자동 단계 변경 | 인수 중/인수 승인 현장의 근거가 만료·회수·실패하면 `suspended`로 바꾸고 감사 이력 기록 |

자동 단계 변경은 관리 DB의 인수 상태에 적용된다. 기존 하드웨어 게이트웨이는 계속 검수 대기이며, 이 기능은 로컬 비상정지나 실제 장비 제어·안전회로를 대체하지 않는다. 매분 점검은 안전 제어 주기가 아니다. 개인정보·장비키·결제 데이터·원본 특허자료를 새 테이블에 복제하지 않는다.

## 검증 및 재현

```sh
npm ci
npm run test:contracts
npm run test:database          # 기존 일반 OS 계정에서 로컬 PostgreSQL 17.10
npm run test:database:wasm     # root 전용 실행 환경의 WASM PostgreSQL 대안
npm run build
```

로컬 확인 결과: 웹 계약 시험 55개, WASM PostgreSQL 18.6 SQL 시험 57개, Python 모형 시험 167개 통과. native PostgreSQL 17 동시성 시험은 CI 정의에 포함했으며 원격 실행 결과 확인 후 배포한다. [검증 기록](verification/governance-validation.json)에 범위와 마이그레이션 해시를 고정한다.

두 DB 시험기는 항상 새 로컬 DB를 만들며 운영 DB 접속 문자열·프로젝트 ID를 받지 않는다. 실제 SQL 구현과 고정 카탈로그를 적용하고, 최소 Supabase Auth/역할 fixture 위에서 RPC 권한과 상태 전이를 검사한다. hosted Auth의 JWT 서명 검증·MFA 서비스, PostgREST, Realtime, Storage, pg_cron 설치/실행은 로컬 fixture의 검증 범위가 아니다. WASM은 단일 연결이며 동시 트랜잭션 경합은 native PG17 runner에서만 검사한다.

CI 정의에 프런트 계약 시험, native PostgreSQL 17 DB 시험, 기존 Python 모형 시험, 프로덕션 빌드를 연결했다. 새 CI의 실제 실행은 원격 저장소 반영 후 확인해야 한다. 성공한 CI는 현장 HIL·SAT 승인으로 계산하지 않는다.

검증 항목: 두 조직·현장 교차 접근, 위조 사용자 메타데이터, MFA 부족, 읽기 전용 역할, 권한 회수·만료, 중복 등록·내용 충돌, 원자적 단지/이벤트 생성, worker 중복 방지·부분 실패·5회 제한, 자기 검수 거부, 승인 불변, 증거 만료, 모의 결과의 현장 시험 오인 방지, 새 실패의 기존 인수 무효화, 재시험 연결·독립 완료, 소스 변경의 승인 분리, 부족한 증거의 현장 승격 거부, 자동 중지 감사, 고정 분모.

## 적용·복귀 순서

1. 검토 브랜치의 계약·DB·빌드 시험 성공을 확인한다. 변경 전 현장 데이터는 0개였으며 이번 마이그레이션은 기존 데이터를 삭제하지 않는다. 새 DB 백업 생성·복원 시험은 이번 검증에 포함하지 않았다.
2. 승인된 경우 `supabase/migrations/20261018230357_add_platform_feedback_governance.sql`의 정확한 내용을 마이그레이션으로 적용한다. 이 단계 전에는 웹 변경을 main에 병합하지 않는다.
3. 운영 서버의 함수·GRANT·RLS와 익명/잘못된 역할 거부를 읽기/롤백 시험으로 확인한다. `pg_cron` 작업의 실제 첫 실행과 오류 유무를 확인한다.
4. 웹 변경을 main에 병합하고 Cloudflare 배포 결과를 확인한다.
5. 실제 두 관리자 계정의 MFA 세션과 승인된 검증용 현장으로 UI 흐름을 인수한다. 시험 데이터에는 검증용임을 명시하고 실장비 기록으로 집계하지 않는다.
6. 문제가 있으면 웹을 이전 버전으로 복귀하고 새 RPC의 실행 권한과 두 예약 작업을 중지한다. 증거·감사 이력은 삭제하지 않는다. 현장의 `ready` 상태를 무조건 복원하지 않는다.
