# 기업 문의 계약 초안 — WEB-01-CONTRACT

후속: 관리자 API의 구현 대상은 [관리자 계약 v1](inquiry-admin-v1.md)로 고정했다. 아래 공개 접수 동의·재시도 제안은 아직 후속 단계다.

상태: 소스 조사 완료, 차기 서버/UI 구현을 위한 제안 v0.1. 이 문서에 제안한 RPC와 권한은 아직 배포되지 않았다. 기반 `bc01dcad57bf298612cab7e3e4456d23d2a08789`, 담당 Codex, UX 분석·교차 검토 Claude. 추적 #23, #25, #26, #24.

## 확인한 현재 흐름

- `src/corporate/CorporateInquiry.tsx`: 세션 저장이 없는 별도 anon 클라이언트로 `inquiries`에 INSERT한다. 필수 입력과 동의 체크, 동시 제출 방지, 20초 제한이 있다. 네트워크 결과 불명 시 재시도로 중복될 수 있다. 동의 체크는 현재 서버에 증빙으로 저장되지 않는다.
- `src/components/ContactSection.tsx`: 공유 클라이언트로 INSERT한다. 로그인된 사용자는 다른 DB 역할이므로 공개 폼과 같은 권한이라고 가정하지 않는다.
- `src/admin/pages/InquiryList.tsx`, `InquiryDetail.tsx`: 테이블 직접 조회·갱신·삭제를 사용한다. 메모·이력 배열은 클라이언트에서 덮어쓰며 담당자 문자열은 서버가 확인한 사용자 ID가 아니다. 답변 처리는 DB 저장이며 실제 이메일/SMS 발송을 하지 않는다.
- `AdminPageGate`가 문의 경로를 포함한 미연결 기능의 운영 노출을 제한한다. 이번 UI 수정은 이 게이트를 열지 않는다.
- `supabase/migrations/20260515042020_create_inquiries_table.sql`의 옛 authenticated 정책은 로그인만으로 읽기·갱신·삭제를 허용한다. 2026-10-22 실제 DB 읽기 전용 확인에서는 그 옛 정책 대신 `inquiries_admin_all`이 `private.is_platform_admin()`으로 제한하고 있다. anon은 company/name/phone/email/project_type/message 열 INSERT만 허용되며 테이블 단위 INSERT 권한은 false다. 따라서 테이블 권한만 보고 공개 폼이 막혔다고 판단하면 안 된다. 이 집계는 실제 REST 제출 성공을 대신하지 않는다.
- `supabase/sql/platform-foundation.sql`의 `sgp_service_requests`는 인증 사용자 ID, UUID 재시도 키, 종류와 길이 제한, MFA 관리자 검토, 감사 기록을 갖는 별도 앱 요청이다. 익명 기업 문의를 가짜 회원 ID로 변환해 넣지 않는다.

## 다음 구현의 공통 계약 제안

| 영역 | 제안 |
|---|---|
| 익명 접수 | 서버 입력 검증과 서버가 부여하는 초기 상태. 연락처·내용·유형·동의 버전·동의 시각, UUID 재시도 키를 받되 관리자 전용 필드는 거부한다. 공개 응답에는 다른 문의의 개인정보나 조회 토큰을 포함하지 않는다. |
| 재시도 | 같은 키·같은 내용의 중복 생성 방지. 같은 키·다른 내용은 충돌. timeout은 접수 실패로 단정하지 않고 결과 미확인 안내. 익명 키가 다른 사용자의 접수를 조회하는 수단이 되지 않도록 설계한다. |
| 관리자 | 서버에서 검증한 관리자 권한과 MFA 필요. 문의 조회·배정·메모·상태 변경마다 actor ID와 서버 시각으로 감사한다. 일반 회원·anon·비MFA 관리자는 관리자 변경 불가. |
| 상태 | `접수대기 → 검토중 → 답변완료`, 보류와 재개는 명시적 명령. 종료 상태의 재개·정정은 별도 기록. 답변 저장과 외부 전달 성공을 별도 필드/이벤트로 기록한다. |
| 동시성 | `expected_revision`과 UUID command ID로 중복 명령과 다른 관리자의 오래된 수정 충돌을 검출한다. 메모는 추가 방식이며 브라우저가 전체 이력을 덮어쓰지 않는다. |
| 앱 요청 연결 | 기업 문의와 앱 요청의 출처를 유지하고 통합 관리자 읽기 모델에서 구분한다. 연결할 현장이 없을 때 무소속 상태를 유지한다. 본인확인 없이 자동으로 입주민 계정에 귀속하지 않는다. |
| 삭제·보존 | 파괴적 일괄 삭제는 차기 UI의 기본 동작에서 제외한다. 실제 보존 기간·접근 담당자·외부 전달 채널은 운영자가 확정해야 하며 문서에서 임의로 결정하지 않는다. |
| 오류 | validation / authentication / MFA / permission / revision-conflict / duplicate-conflict / rate-limit / temporary-unavailable을 구분한다. 응답·로그에 연락처·내용·토큰을 노출하지 않는다. |

정확한 RPC 이름·JSON 스키마·마이그레이션은 #25 구현 전에 계약 시험과 함께 확정한다. UI는 그 버전을 기준으로 구현한다. 외부 발송은 제공사·발신자·운영 동의가 확인된 후 연결한다.

## 필수 검증과 인계

1. 폐기 가능한 PostgreSQL에서 anon·일반회원·관리자 aal1·관리자 aal2 권한을 검증한다. 우회 직접 테이블 접근과 API 접근을 모두 시험한다.
2. 중복·내용 충돌·동시 메모·이전 revision·상태 전이·감사 이벤트·길이 경계·잘못된 유형을 시험한다. 시험 자료는 합성으로 표시한다.
3. Claude는 로그인 유무별 접수, 실패 시 입력 유지, 모든 유형 표시, 상태/답변 문구, 키보드 및 모바일 UI를 검증한다.
4. Codex는 DB/RPC, 기존 요청과의 분리·연계, migration/rollback 검토 및 CI를 맡는다. 경로 해제는 서버 검증과 UI 여정 통과 이후 별도 변경으로 한다.
5. 운영자는 실제 처리 담당자·계정, 보존 기준, 수신 채널을 확인하고 실제 문의 1건의 접수·처리·수신 결과를 인수한다. 이 단계가 끝나기 전 운영 100%로 표시하지 않는다.

## 이번 단계에서 완료한 독립 수정
