# 결제·정산·회계 구현 검증 기록

2026-10-19. 이 기록의 로컬 게이트는 실제 PG·은행·ERP 인수가 아니다.

| 게이트 | 확인 결과 |

## 피드백으로 수정한 내용

- 첫 native PG17 로그에서 지연 제약 트리거가 RPC 종료 후 호출자 권한으로 실행되는 문제를 발견했다. 트리거 검증 함수만 빈 search_path의 SECURITY DEFINER로 바꾸고 직접 실행 권한 차단을 유지했다.
- DB 종료 정리가 시험기의 실패 종료 코드를 덮는 문제를 수정했다. CI는 종료 코드뿐 아니라 마지막 전체 통과 건수도 검사하여 중도 실패를 성공으로 표시하지 않는다.
- 단계별 DB 설치 시 테스트 역할이 남는 문제를 분리하고, 설치는 관리자 역할·호출은 인증 역할로 고정했다.
- 중복 제공자 결과를 재수신해도 기존 결과를 반환하도록 보완했다. 다른 내용으로 동일 영수증을 재사용하면 충돌로 거부한다.
- 화면의 제공자 영수증 식별자는 배치·시도·결과에 고정하여 네트워크 오류 후 재시도 때 다른 요청이 되지 않게 했다.
- 현재 MUI의 입력 API에 맞춰 슬롯 속성으로 수정하고 다시 빌드했다.
- 부분 환불 수수료는 누적 환불액 기준 차액으로 계산하여 최종 환불이 원결제의 수수료·시설 몫과 정확히 일치하게 했다.
- 음수 시설 조정은 새 지급으로 처리하지 않고 다음 양수 정산과 상계했다.
- CSV의 수식 시작 문자·따옴표·개행을 보호하고 JSON은 서버의 정규 문자열 SHA-256과 대조한 뒤 내려받는다.

## 재현

```sh
npm ci
npm run test:contracts
node scripts/test-finance-database.mjs --wasm --stage=1
node scripts/test-finance-database.mjs --wasm --stage=2
npm run test:finance:wasm
npm run test:finance  # 기존 일반 OS 계정의 disposable PostgreSQL 17.10
npm run test:database
npm run build
```

DB 시험기는 운영 DB 주소·접속 키를 받지 않는다. Supabase Auth 서명·MFA 서비스 자체는 로컬 fixture로 대체하므로 실제 인증 인수와 구분한다. WASM PostgreSQL은 18.6이며 native PG17 동시성 결과는 PR CI 로그에 기록한다.

## 한계와 후속 게이트

- 최고관리자 두 계정의 시험 워크벤치다. 일반 사용자 실결제 화면은 계속 준비 중이며, 실제 고객 잔액·기존 코인 원장은 변경하지 않는다.
- 수취 운영사는 시험 시설에 고정한다. 실제 법인·은행계좌·KYC 확인과 현장 매핑은 실제 연동 단계에서 별도로 인수한다.
- 단위 요금·수수료 bps는 시험 계약이다. 실제 이용시간은 신뢰 가능한 장비/운영 세션에서 확정해야 한다.
- 전표는 내부 복식부기 모형이다. 부가세·PG 수수료·세금계산서·본사/현장 법인별 회계 정책을 확정한 완전한 ERP가 아니다.
- JSON/CSV는 DOELV 교환 형식이고 ERP 모의 수신 확인은 실제 ERP에 입력됐다는 의미가 아니다.
- 글로벌 DB 잠금으로 작은 시험 원장을 직렬 처리한다. 실거래 규모의 성능/SLA 검증 없이 운영용 동시 처리 성능을 주장하지 않는다.
- 실패한 모의 지급은 동일 제공자 키로 최대 5회 요청할 수 있으며, 미확정 지급은 자동 재지급하지 않는다. 외부 제공자 서명 검증·웹훅·취소/회수 API·은행 대사·장애 복구 인수는 단계 5에 남는다.

운영 적용과 최종 배포 SHA·CI 결과는 이 변경의 GitHub PR 본문에서 확인한다. 새 테이블은 19개이며 비공개 스키마/RLS/직접 접근 차단을 적용한다. 공개 RPC 3개는 최고관리자 DB 역할과 MFA를 매번 검사한다. 일정 작업과 실제 송금 기능은 추가하지 않는다.
