# 단지·회원 운영 업무 1차 구축

2026-10-21 KST · 통합 계획 P1 / T01·T02·T03의 일부 · 전체 플랫폼 인수와 별도.

이전에는 `/admin/complexes`와 `/admin/residents`가 상위 게이트에서 차단됐고 기존 테이블에 연결된 화면만 남아 있었다. 두 경로를 신규 공통 현장 ID와 실제 DB 역할을 검사하는 업무 화면으로 교체한다. 기존 `complexes`와 `resident_accounts` 행을 신규 현장·회원으로 자동 이전하거나 합치지 않는다.

## 구현 범위

| 화면 | 실제 서버 작업 |
|---|---|
| 관리자 → 단지 관리 | 허용 현장 선택, 운영 주소·관리사무소 연락처·안내 시간 저장, 소속 현황·변경 이력 |
| 관리자 → 사용자 | 초대코드 발급·폐기, 신청 검토·승인·반려, 소속 회수, 상태 필터·50건 단위 조회 |
| 공식 앱 → 설정 | 초대코드로 소속 신청, 최근 신청 30건과 처리 사유 확인, 승인 전 철회, 내 소속 조회 |

현장 안내정보는 안내용이다. 자동 제어 시간표·안전 정책·현장 단계·장비 권한을 변경하지 않는다. 소속 승인은 플랫폼 회원 연결이며 실제 출입권·주차 운행·코인 결제 권한을 발급하지 않는다. `sandbox` 표시는 유지된다.

## 설정·사용 순서

1. 최고관리자가 현장 검증·개선에서 조직을 만들고 단지 템플릿 생성으로 현장을 등록한다. 담당자는 실제 운영 계정의 DB 역할과 현장 manager 배정·유효기간을 부여받고 AAL2 인증을 완료한다. viewer·reviewer는 조회만 가능하다.
2. 단지 관리에서 현장을 선택하고 안내정보를 저장한다. 회원 관리 바로가기는 동일한 현장 ID를 전달한다.
3. 회원 관리의 초대코드 탭에서 1~7일·최대 100회 신청 범위로 코드를 발급한다. 원문은 최초 응답과 현재 화면의 메모리에만 존재하고 DB에는 해시만 저장한다. URL·브라우저 저장소·감사 로그·재조회 응답에 원문을 넣지 않는다. 최초 응답을 잃으면 목록에서 해당 발급을 폐기하고 새 코드를 발급한다. 발급된 코드를 대상자에게 전달하는 일은 운영자가 직접 수행한다.
4. 실제 문자 인증이 완료된 활성 회원이 공식 앱 설정에서 초대코드와 동·호 또는 이용 구분을 입력한다. 코드를 알고 있어도 신청만 생성되며 현장 조회 권한은 생기지 않는다. 잘못된 현장에 신청했으면 승인 전에 철회한다.
5. 현장 담당자가 실제 입주·이용 자격을 확인하고 사유 5~500자를 적어 승인 또는 반려한다. 문자 인증은 휴대전화 소유 확인이며 입주 자격 증명·PASS 본인확인과 구분한다. 본인의 소속 신청은 스스로 승인할 수 없다.
6. 이사·이용 종료 시 회원 목록에서 소속 회수와 사유를 기록한다. 해당 현장의 회원 소속과 차량 확인 상태를 함께 회수하고 다른 현장의 소속은 유지한다. 되돌리려면 새 신청과 자격 확인을 거친다.
7. 변경 이력과 회원의 내 소속을 다시 조회해 대조한다. 건물·구역·구조화된 세대 원장과 계정 탈퇴·개인정보 삭제 정책은 후속 범위다.

## 서버 계약과 복구

- `platform_membership_command`: `profile`, `issue_invite`, `revoke_invite`, `apply`, `withdraw`, `review`, `revoke_member`. 실제 호출자·문자 인증 상태·현장 역할·AAL2를 동작별로 검사한다. 클라이언트가 보낸 user_id나 역할을 승인 근거로 사용하지 않는다.
- `platform_membership_snapshot`: 담당 현장의 요청·회원·초대·이력만 조회한다. 종류·상태·UUID 커서로 최대 50건을 반환한다. 전화번호·이메일·생년월일·인증 원문은 반환하지 않는다.
- `platform_my_memberships`: 본인의 소속과 최근 신청 30건만 조회한다.
- 모든 변경은 같은 트랜잭션의 상태 변경·명령 영수증·현장 이력·감사 기록으로 연결된다. 요청 UUID와 내용 해시가 같은 재시도는 원래 영수증을 반환하고 다른 내용은 충돌로 거부한다. 영수증은 당시 작업 결과이며 현재 소속 권한을 증명하지 않는다. 화면은 처리 후 현재 상태를 재조회한다.
- 관리자 변경은 서버 revision을 확인한다. 동시에 변경된 화면에서는 최신 조회 후 다시 처리한다. 초대 폐기와 신청의 잠금 순서를 현장→초대 행으로 통일한다. 하위 상태 갱신 실패는 상위 승인도 함께 롤백한다.
- 초대 만료·폐기·사용 한도, 회원별 시간당 신청 5회, 현장별 시간당 초대 발급 20회를 검사한다. 중복 신청은 허용하지 않는다. 철회된 신청도 초대 사용 횟수와 남용 방지 이력에 남는다.
- 문자 인증 상태와 시각은 기존 서버 전용 가입 절차의 `sgp_users` 필드로 검사한다. 브라우저에 이 필드를 변경할 권한을 추가하지 않는다. 일반 회원은 직접 membership 테이블을 수정할 수 없다.
- 현장 전환·계정 전환 시 이전 쿼리·발급 코드·처리 대상을 폐기한다. 조회 실패는 빈 목록이나 이전 현장의 정상 상태로 표시하지 않는다. 불확실한 변경 응답은 같은 요청 UUID로 재시도한다.

## 검증과 남은 인수

실제 React 화면과 폐기 가능한 PostgreSQL/WASM에서 안내정보 저장→초대→회원 신청→승인→회수→본인 이력 확인을 연결한다. 별도 SQL 계약은 현장 격리, MFA·문자 상태, 자기 승인 거부, 역할 회수 후 이전 세션 거부, 재시도·버전 충돌·50건 페이지, 철회·반려·만료·폐기, 하위 오류 롤백과 회수를 확인한다. CI는 PostgreSQL 17에서도 같은 DB 계약을 수행한다.

가상 DB의 인증 클레임과 문자 확인 상태는 명시적인 테스트 픽스처다. 운영 DB에 가상 문자 인증 성공 기록·입주 자격 증빙·기존 Auth 계정을 삽입하지 않는다. 실제 문자 수신·가입, 실제 운영자에 의한 입주 자격 판단과 승인·이사 처리 인수는 별도로 필요하다. T03 전체나 36개 요구사항의 운영 인수를 자동 승인하지 않는다.
