# 건물·세대 원장과 회원 승인 연결

2026-10-22 KST · P1 / T01·T03 보강. 전체 플랫폼·현장 인수를 의미하지 않는다.

기존 회원 신청은 동·호 또는 이용 구분을 자유 입력했고, 승인된 소속에도 공통 세대 ID가 없었다. 이번 변경은 현장 → 건물 → 세대의 기준 ID를 만들고 담당자가 확인한 세대를 승인 시점에 연결한다. 기존 단지·회원·금융 시설·장비 ID를 이름만으로 자동 병합하지 않는다.

## 설정과 사용

1. 관리자는 2단계 인증 후 단지 관리에서 담당 현장을 선택한다. 조회 역할은 원장을 조회할 수 있고 변경은 현장 manager 또는 본사 최고관리자만 가능하다.
2. 건물·세대 원장에서 건물을 등록한다. 건물 버튼을 선택하고 해당 건물의 세대를 등록한다. 각 명칭은 1~30자이고 같은 현장의 건물명, 같은 건물의 세대명은 중복되지 않는다. 명칭은 고정된다. 오기는 기존 항목을 중지하고 새 항목을 등록해 고친다.
3. 이미 활성 회원이 있다면 회원 목록의 **등록 세대 연결·변경**에서 실제 자격을 확인하고 건물·세대와 사유를 선택한다. 본인의 세대 연결은 다른 관리자가 처리한다. 문자 확인 상태와 실제 자격은 서로 다른 확인 사항이다.
4. 원장 미연결 활성 소속이 0명이고 사용 중인 건물·세대가 준비되면 변경 사유를 적고 **등록 세대 필수로 변경**한다. 기존 소속의 상태나 권한을 자동 변경하지 않는다. 독립 주차시설 등 자유 이용 구분이 필요한 현장은 자유 입력 방식을 유지할 수 있다.
5. 회원은 기존 공식 앱 설정에서 초대코드와 동·호 또는 이용 구분을 적어 신청한다. 입력 내용은 신청자의 주장으로 보존된다. 회원은 전체 세대 원장을 열람하거나 원장 ID를 스스로 확정하지 못한다.
6. 관리자 회원 신청 화면에서 실제 자격을 확인하고 소속 승인을 연다. 등록 세대 필수 현장은 **승인할 등록 건물 → 승인할 등록 세대 → 처리 사유**를 모두 선택해야 한다. 자유 입력 현장에서도 선택하면 원장에 연결할 수 있다. 세대마다 가족 등 여러 회원을 연결할 수 있으며 소유권·세대주 지위를 자동 부여하지 않는다.
7. 승인 후 회원 목록과 회원의 내 소속에서 확정된 동·호를 확인한다. 신청 내역에는 원래 입력한 내용이 보존된다. 과거 승인·연결 ID는 기록에 남고 재신청은 새 자격 확인을 거친다.
8. 세대 사용 중지는 활성 소속을 회수하거나 실제 자격 확인 후 다른 세대로 연결한 뒤 처리한다. 건물 중지는 모든 세대를 중지한 뒤 가능하다. 재개는 건물부터 처리하고 필요한 세대를 각각 재개한다. 과거 원장·연결 기록을 삭제하지 않는다.

## 오류와 복구

- 다른 현장·중지된 건물/세대 선택은 서버가 거부한다. 선택 후 다른 관리자가 세대를 중지한 경우 승인 전체가 롤백되므로 원장을 다시 조회하고 자격·선택을 확인한다.
- 변경 사유는 5~500자다. 변경 충돌은 새로 조회한 revision으로 다시 처리한다. 불확실한 전송 결과에 대한 같은 내용의 재시도는 같은 요청 UUID를 사용한다. 기존 영수증을 재조회해도 현재 역할을 서버에서 다시 확인한다.
- 조회 실패는 이전 원장이나 빈 원장을 정상 상태처럼 표시하지 않는다. 현장·계정 전환 시 선택과 대기 응답을 버린다. 건물과 세대는 식별자 순서로 최대 50건씩 조회하므로 다음 페이지도 확인한다.
- 원장 필수 방식으로 변경할 수 없으면 사용 중인 건물·세대가 있는지, 활성 소속의 미연결 건수가 0인지 먼저 확인한다. 소속을 임의 회수해 건수를 맞추지 말고 담당자가 실제 자격을 판단한다.

## 서버와 검증 범위

- `platform_private.site_buildings`, `site_units`, `site_residence_policies`는 RLS를 켜고 직접 클라이언트 권한을 부여하지 않는다. 복합 외래키 `(site_id,building_id)`·`(site_id,unit_id)`가 현장 간 연결을 DB에서도 거부한다.
- `platform_residence_directory`는 AAL2와 실제 담당 역할을 검사하고 최대 50건을 반환한다. 일반 회원은 승인된 소속이 있어도 전체 원장과 활성 소속 건수를 조회하지 못한다.
- 기존 `platform_membership_command`의 동일한 actor·현장 잠금, 요청 해시, revision, 감사 트랜잭션 안에 원장 변경을 연결한다. 실제 서버 역할·문자 확인 상태·독립 승인 검사는 유지한다. 새 `unit_id`는 기본 null이며 기존 회원을 자동 연결하지 않는다.
- 승인 당시 확정된 동·호는 회원 소속에 저장하고 신청 당시 입력 내용은 요청에 보존한다. 원장 사용 중지는 활성 소속을 끊지 않고, 다른 현장 소속·차량·정산 데이터를 변경하지 않는다.
- 폐기 가능한 실제 SQL DB와 React 화면으로 등록→필수 방식 설정→신청→승인 전 세대 중지→승인 거부·롤백→원장 재개·재조회→승인·본인 소속 대사를 검증한다. 현장 격리·위조 메타데이터·MFA·조회 역할·독립 승인·외래키·중복/재시도·버전 충돌·51건 이상 페이지·회수 후 이력 보존도 검증한다. CI는 PostgreSQL 17에서 기존 회원 업무와 새 원장 계약을 함께 수행한다.
- 가상 인증·문자 확인은 폐기 가능한 테스트 DB에만 사용한다. 운영에서 실제 문자 수신·입주 자격 확인·운영 담당자의 인수와 회원 탈퇴·보존 정책은 여전히 완료 대상이다. 소유권·출입권·장비 운행·결제 권한의 인수를 대신하지 않는다.

SQL 원문: `supabase/sql/site-residence-directory.sql`. 적용 시 서버가 기록한 실제 migration 버전을 별도로 동기화한다.
