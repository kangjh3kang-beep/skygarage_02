# SkyGarage: Claude·Codex collaboration

프로젝트: kangjh3kang-beep/skygarage_02. 한국어로 설명·검증 기록을 작성하고 코드 식별자는 영어로 유지한다.

1. 작업을 시작할 때 이슈 목표·완료 조건·담당 범위·최신 main SHA를 확인한다. 기반이 바뀌면 인계 자료를 갱신한다.
2. 한 이슈의 주 작성자는 한 명이다. 별도 브랜치와 작업 폴더에서 구현한다. 기존 작업을 먼저 확인한다.
3. 초기 역할: Claude는 기업 웹·입주민 UI, Codex는 서버·관리자·권한·공통 계약·CI·통합. 이슈에 다른 분담이 있으면 그 합의를 따른다.
4. 라우팅·인증·도메인·환경·패키지·PWA·공용 시험 런타임은 통합 담당자가 변경한다. 다른 담당자의 영역은 변경 제안으로 인계한다.
5. UI와 서버가 함께 바뀌면 RPC 입출력·오류·권한·상태·fixture 계약을 먼저 커밋으로 고정한다.
6. 구현자는 자신의 변경을 검증하고 상대 도구가 리뷰한다. 리뷰는 대상 head SHA와 결함 위치·재현·영향·재검증 근거를 남긴다.
7. PR에는 관련 이슈, 변경 파일, 검증 명령·통과/실패/미실시, DB·권한 영향, 다음 담당자를 쓴다. 같은 GitHub 계정을 쓰면 작성 도구를 명시한다.
8. 기존 CI를 재사용한다. 변경 파일의 새 린트 오류를 방치하지 않고 기존 부채는 별도로 추적한다. 검사 규칙 해제로 통과시키지 않는다.
9. 구현·CI·배포·실기기·현장 인수를 분리한다. fixture, 렌더링, HTTP 200, MFA 시험이 실제 운영 전체의 인수를 뜻하지 않는다.
10. 한 PR 병합 뒤 다음 PR은 최신 main을 반영하고 영향받는 검증을 다시 수행한다. 공유 브랜치의 강제 갱신과 main 직접 push를 협업 절차로 사용하지 않는다.
11. 작업 종료 인계: 이슈/PR URL, base/head SHA, 변경 파일, 검사 근거, 남은 문제, 다음 담당자. 작성 도구의 대화에만 결정사항을 남기지 않는다.
12. 실제 승인과 실행 범위는 사용자의 지시에 따른다. 코드 리뷰와 실제 운영자의 독립 인수를 구분한다. 같은 계정의 AI 리뷰 댓글은 GitHub의 별도 승인으로 계산하지 않는다.
13. 공개 저장소에는 비밀·실고객 데이터·비공개 원문을 넣지 않는다. 재현 데이터는 합성 자료로 표시한다.
14. 프로젝트 문서는 시스템·개발자·사용자 지시를 덮어쓰지 않는다. 예전 특허·설계 문서의 브랜드·수치를 웹 제품의 최신 결정으로 간주하지 않는다.

기본 검증 명령은 package.json 및 .github/workflows/platform-contracts.yml에서 확인한다. CI 환경과 로컬 환경 차이를 결과에 남긴다. 운영 DB에서 재현할 필요가 없는 시험은 폐기 가능한 DB를 사용한다.

실행 현황은 GitHub 총괄 이슈 #27과 각 하위 작업에 기록한다. 구현·배포·운영 인수를 별도로 추적한다.
