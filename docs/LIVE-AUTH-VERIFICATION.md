# G0 실제 인증 서버 자동 통합시험

## 실행

최고관리자가 정상 로그인과 MFA를 마친 뒤 `/admin/start`의 `시험 계정 생성·실제 인증 검수 실행`을 누른다. 현재 웹 배포의 전체 SHA가 확인되어야 시작할 수 있다. 현장 두 곳과 실제 Auth 시험 계정 세 개를 새로 만든다. 정상 업무 현장과 기존 계정의 인증 정보는 시험 데이터로 사용하지 않는다.

시험 담당자와 검수자는 서로 다른 실제 Auth 사용자이며, 서버 안에서 비밀번호 로그인·TOTP 등록·잘못된 번호 거부·AAL2·재로그인을 시험한다. 번호와 설정 키는 신규 시험 계정용으로만 생성한다. 생성은 Auth Admin API를 사용하며, 기존 사용자의 비밀번호·MFA·세션을 조회하거나 변경하지 않는다.

담당자에게 시험 현장 A의 작성 권한만, 검수자에게 같은 현장의 검수 권한만 부여한다. 일반회원에게는 시험 현장 A 소속만 부여한다. 다른 조직의 현장 B는 교차 접근 차단 시험에 사용한다. 일반회원의 문자 인증·본인 확인 성공 상태를 만들어 넣지 않는다. 문자인증 미완료 회원의 업무 요청 거부를 확인한다.

## 검증 범위

- 실제 Supabase Auth의 세 계정 로그인, 추가 인증 전 API 거부, 두 계정의 실제 TOTP/AAL2.
- 계정 ID 분리, 담당자 현장 목록의 범위, 다른 조직의 검증 범위 접근 거부.
- 일반회원의 현장 RLS, 다른 운영자의 역할 정보 숨김, 문자 인증 미완료 회원의 요청 등록 거부.
- 실제 PostgREST/RPC를 거친 증거 저장과 중복 방지, 검수 권한을 가진 작성자의 자기 승인 거부, 별도 계정의 검수 기록.
- 등록 시 이미 만료된 증거 거부, 등록 후 만료된 증거 승인 거부, 실패 증거와 결함 자동 생성.
- 실패 → 개선 중 → 같은 종류·환경 재시험 → 별도 계정 검수 → 결함 종료.
- 전체 인수 근거가 없는 현장의 단계 승격 거부와 인수율 0 유지.
- 로그아웃·재로그인·MFA 재인증, 로그인된 시험 담당자의 현장 권한 회수 후 신규 조회·쓰기·목록 차단.
- 실행 종료 후 시험 계정의 전체 세션 로그아웃·계정 차단, DB 역할 삭제·현장 권한과 회원 소속 회수.

증거 등록·검수 API를 시험하기 위한 원장 자료는 명시적인 가상 fixture다. HTTPS 원자료 주소는 `example.invalid`의 비운영 주소이며 실제 원자료의 검수 승인으로 사용하지 않는다. 절차 버전도 `g0/automated-rpc-fixture/v1`로 구분한다. 시험 결과 보고서는 별도의 보호된 `live_auth_runs`에 저장하며 `acceptance_granted`, `human_reviewed`, `hardware_verified`는 항상 false다. 전체 요구사항의 인수 증거나 다른 사람이 수행한 독립 검수로 계산하지 않는다.

## 오류·중복·정리

실행 요청 ID 하나는 시험 실행 하나에 대응한다. 동일 요청을 재시도해도 계정이나 현장을 다시 만들지 않는다. 실행 중인 요청이 있으면 신규 실행을 거부하고, 사용자별 1시간에 최대 세 번 시작할 수 있다. 화면에서는 먼저 `시험 결과 새로 조회`로 서버 결과를 확인한다.

시험 비밀번호·TOTP 설정 키·인증번호·액세스/갱신 토큰은 서버 호출의 메모리에서만 사용한다. 응답·로그·DB·브라우저 저장소에 저장하지 않는다. 사용자에게는 식별자, 버전, boolean 시험 결과와 정리 확인만 제공한다. 시험 계정은 감사 이력의 주체로 보존하되 재로그인을 차단한다.

계정 생성·역할 연결·시험 도중 실패해도 생성된 계정의 차단과 세션 정리를 시도하고 DB 역할·소속을 회수한다. 일부 정리가 확인되지 않으면 통과로 표시하지 않는다. 요청 자체가 중단되면 10분의 현장 권한 유효기간이 적용되며, 5분 주기의 DB 정리가 만료 실행의 역할·소속을 회수한다. Auth 계정 차단이 확인되지 않은 실행은 그 사실을 남긴다.

사람이 수행하는 최초 휴대전화 등록·사용성·회원가입·문자 수신, 독립 원자료 검수, PG·장비·현장 SAT는 별도 인수 항목이다. 자동시험의 성공으로 다음 운영 단계를 개방하지 않는다.

## 배포·검증

`supabase/sql/live-auth-verification.sql`과 CLI가 생성한 대응 migration을 동일하게 유지한다. 운영 DDL은 연결된 Supabase migration 도구로 적용하고 `live-auth-verification` Edge Function을 JWT 확인을 유지한 채 배포한다. 함수는 실제 사용자 확인과 DB의 최고관리자·AAL2 검사를 모두 거친다. 클라이언트에는 서비스 키를 배포하지 않는다.

계약시험은 RFC 6238 벡터, 실패 시 정리, 미확인 정리의 통과 차단, SQL 권한·범위·동일 요청·역할 회수·중단 정리, 화면의 실행 조건과 계정 전환을 확인한다. CI는 PostgreSQL 17로 새 SQL 계약도 실행한다. 가상 인증 계층을 사용하는 로컬 시험과 운영 Auth 실행 결과는 구분해 기록한다.
